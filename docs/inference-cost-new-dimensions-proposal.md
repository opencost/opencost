# OpenCost Inference Costs: New Dimensions Proposal
Author(s): @simanadler

Add requestor, tenant, and workload tracking to the OpenCost inference cost capabilities based on metrics generated by the [llm-d](https://llm-d.ai/) [Inference Payload Processor (IPP)](https://github.com/llm-d/llm-d-inference-payload-processor).

See the following related documents:

- **[IPP Proposal for New Metrics](https://github.com/simanadler/llm-d-inference-payload-processor/blob/6d6f160ad969a9ad2761246f09a947e82e23d51c/docs/proposals/044-request-attribution-metrics/README.md):** — covers the extensions required to llm-d's Inference Payload Processor (IPP) to generate the new metrics.
- **[OpenCost current inference cost capabilities](./docs/inference-cost-tracking.md)** — the existing model-level inference cost solution this plan extends.

## 1. Background & Goal

### Business need

As self hosted AI model deployments grow to serve multiple teams, applications, and external customers, platform operators need answers that raw infrastructure metrics cannot provide:

- **Chargeback** — which tenant or workload is responsible for what share of the GPU bill?
- **Showback** — give each team visibility into its own consumption without exposing the full cluster cost view.
- **Capacity planning** — which workloads are growing fastest, and which models are they driving load on?
- **Quota enforcement** — detect when a single requestor or workload is crowding out others before it becomes an incident.

### The five signal dimensions

IPP sits in the request/response hot path as an Envoy ext-proc service and is the only component in the llm-d stack that simultaneously sees both the identity of a request (HTTP headers) and the token consumption of its response. The dimensions it enables us to capture are:
* **Requestor** 
* **Tenant** 
* **Workload** 
* **Requested model** 
* **Serving model** 

The guiding principle, stated in the IPP spec:

> **IPP owns identity + volume. vLLM owns model-level throughput. OpenCost owns cost.**
> Attributed cost is the join: Ex: `tenant_tokens × (cost_per_million_tokens ÷ 1,000,000)`. IPP never computes or stores a cost value.



### Prerequisite: IPP deployment

Two distinct cost types are available in an llm-d deployment that is cost enabled (via OpenCost):

| Cost type | What it covers | Requires IPP? |
|---|---|---|
| **Infrastructure cost** | Total GPU/CPU/RAM spend per model per namespace | No — OpenCost derives this directly from vLLM metrics and K8s allocation |
| **Attributed cost** | Infrastructure cost broken down by tenant, workload, or requestor | Yes — IPP is the only component that sees both identity headers and response token counts |

For attributed cost to be accurate:
1. llm-d's IPP must be deployed and in the request path for every inference request.
2. All inference requests must be routed through IPP — any client bypassing the gateway is counted in `vllm:prompt_tokens_total` (and therefore in infrastructure cost) but not in any attributed counter. The data quality check in §5.5 is designed to detect this gap.
3. Clients must propagate `x-tenant-id`, `x-user-id`, and `x-workload-id` on every request. Requests without these headers appear with empty label values but are not attributed to a specific consumer.

## 2. New Outputs

### 2.1 New Prometheus metric: `llm_dimension_hourly_cost`

A new Prometheus gauge will be exported by OpenCost's background collector, complementing the existing three model-level gauges:

```
# HELP llm_dimension_hourly_cost Hourly infrastructure cost attributed to an inference
# request dimension (requestor, tenant, workload). Computed using the IPP token-cost join:
# promptTokens × (inputCostPerM / 1M) + completionTokens × (outputCostPerM / 1M).
# cost_basis=allocation reconciles to bill; cost_basis=usage is active compute only.
# requestor label is empty when IPP is configured with prometheusRequestorLabel: false.
# TYPE llm_dimension_hourly_cost gauge
llm_dimension_hourly_cost{
  model_name="meta-llama/Llama-3-70b-instruct",
  namespace="llm-d-prod",
  cost_basis="allocation",
  requestor="alice@example.com",
  tenant="acme-corp/engineering",
  workload="rag-agent-v2"
} 0.0412
```

Labels: `model_name` · `namespace` · `cost_basis` · `requestor` · `tenant` · `workload`

This metric will only be emitted when `INFERENCE_IPP_METRIC_ENABLED=true`. The `requestor` label is an empty string when IPP is configured with `prometheusRequestorLabel: false` (high-cardinality deployments).

Example PromQL:

```promql
# Top 5 tenants by attributed cost
topk(5, sum by (tenant) (llm_dimension_hourly_cost{cost_basis="allocation"}))
```

### 2.2 New API aggregation and filter dimensions

The existing `/inferenceCost/total` and `/inferenceCost/timeseries` endpoints gain three new values for the `aggregate` and `filter` query parameters:

| New dimension | `aggregate` example | `filter` example |
|---|---|---|
| `requestor` | `?aggregate=requestor` | `?filter=requestor:"alice@example.com"` |
| `tenant` | `?aggregate=tenant` | `?filter=tenant:"acme-corp/engineering"` |
| `workload` | `?aggregate=workload` | `?filter=workload:"rag-agent-v2"` |

These combine with all existing dimensions. Examples:

```
# Cost by tenant across all models, last 7 days:
GET /inferenceCost/total?window=7d&aggregate=tenant&costBasis=allocation

# Hourly per-workload timeseries for one model:
GET /inferenceCost/timeseries?window=24h&accumulate=hour
  &filter=model_name:"meta-llama/Llama-3-70b"&aggregate=workload

# Total cost for a single requestor over 30 days:
GET /inferenceCost/total?window=30d&filter=requestor:"alice@example.com"
```

The response shape is unchanged — `properties` in each `InferenceCostResponse` gains three new optional fields: `requestor`, `tenant`, `workload` (omitted when empty).

## 4. Configuration

### 4.1 New environment variables

One new variable will be added to `pkg/inferencecost/env.go`:

| Env var | Default | Purpose |
|---|---|---|
| `INFERENCE_IPP_METRIC_ENABLED` | `false` | Opt-in to querying IPP metrics and computing dimension-level costs. When false, model-level costs are completely unaffected. |

`INFERENCE_IPP_REQUESTOR_LABEL_ENABLED` is **not** a static env var — it is discovered dynamically per namespace from the `ipp_config_info` Prometheus metric emitted by each IPP deployment. See §4.2 and §5.2.

### 4.2 New `Config` fields

```go
type Config struct {
    // ... existing fields unchanged ...

    // IPPMetricEnabled controls whether IPP metrics are queried for
    // per-requestor/tenant/workload cost breakdown. When false (default),
    // dimension-level costs are not computed and llm_dimension_hourly_cost is not exported.
    IPPMetricEnabled bool
}
```

Per-namespace IPP configuration (whether the `requestor` label is present, which namespaces have IPP deployed) is discovered at collection time by querying `ipp_config_info` — see §5.2.

### 4.3 Multi-llm-d deployments

A cluster may contain multiple independent llm-d deployments, each in its own namespace with its own IPP gateway. Because IPP advertises its configuration via `ipp_config_info`, OpenCost automatically discovers which namespaces have IPP deployed and what their per-namespace settings are — no manual per-namespace configuration is required. See [Appendix B](#appendix-b--multi-llm-d-deployment-issues) for a known pre-existing limitation around shared infrastructure labels.

## Appendices

### Appendix A — Relationship to OpenCost's Existing Allocation Dimensions

OpenCost's base allocation API already supports organisational attribution through **aliased label properties**, backed by Kubernetes pod labels. These are distinct from the new IPP-sourced dimensions.

#### OpenCost's existing aliased label properties

Defined in `core/pkg/opencost/allocationprops.go`, these five properties resolve at query time to configurable K8s label keys via [`LabelConfig`](core/pkg/opencost/config.go):

| OpenCost property | API name | Default K8s label | Closest IPP analog |
|---|---|---|---|
| `AllocationDepartmentProp` | `department` | `department` | tenant |
| `AllocationTeamProp` | `team` | `team` | tenant / workload |
| `AllocationOwnerProp` | `owner` | `owner` | requestor |
| `AllocationProductProp` | `product` | `app` | workload |
| `AllocationEnvironmentProp` | `environment` | `env` | — |

Each label key is configurable (e.g. `TeamLabel = "team,app.kubernetes.io/team,k8s-team"` tries each in order) and supported for aggregation and filtering via the `AllocationMatchCompiler`.

#### Why the new inference dimensions are different

| Characteristic | OpenCost aliased labels | New inference dimensions |
|---|---|---|
| **Source** | K8s pod/namespace labels — static, set at deploy time | HTTP request headers — dynamic, set per request by the caller |
| **Granularity** | Per pod (one value per running container) | Per individual inference request |
| **Who sets it** | Platform operator at deploy time | API client at call time; proxy (IPP/Envoy) forwards them |
| **Visible to allocation layer** | Yes — via `kube_pod_labels` / `kube_pod_annotations` | No — HTTP headers never reach the K8s or OpenCost allocation layer |
| **Collection mechanism** | Prometheus scrape of kube-state-metrics | IPP's `ipp_inference_*_tokens_total` counters |
| **Cost attribution model** | Direct — grouping of existing allocation costs | Indirect — model-level per-million rates applied to per-dimension token counts |

#### Could the existing labels be reused instead?

A pod could be labelled `owner=alice` and then queried with `?aggregate=owner` — this works for coarse pod-level attribution but cannot satisfy the IPP use case because:

- A single model pod serves many requestors simultaneously; a pod label holds one value.
- Workload identity is set by the calling agent at runtime, not pre-provisioned as a pod label.
- Requestor identity is often an email address — not a valid Kubernetes label value.

The existing aliased labels and the new inference dimensions are **complementary**: use the former for static pod-level organisational context, the latter for dynamic per-request attribution. Both can be combined — e.g. `?filter=namespace:"llm-d-prod"&aggregate=tenant`.
